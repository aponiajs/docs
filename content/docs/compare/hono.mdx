  - question: How does Eden Treaty compare to Hono RPC?

Hono's defining decision is portability: one application object that runs on
Cloudflare Workers, Deno, Bun, Node, and Lambda, built on Web standard
`Request` and `Response`. AponiaJS made the opposite decision and targets one
runtime.

<Verdict>
  If you deploy to the edge or to more than one runtime, this is not a real
  choice — take **Hono**. **AponiaJS** only makes sense when Bun is the single
  target and you want structure the framework enforces rather than a convention
  you maintain.
</Verdict>

## Portability is the whole comparison

If any of these are true, the decision is already made and it is not AponiaJS:

- you deploy to Cloudflare Workers, Deno Deploy, or Lambda;
- the same handlers must run in more than one runtime;
- cold start time dominates your latency budget;
- you want the smallest dependency footprint you can get.

Hono is built for that. AponiaJS depends on Bun and on Elysia, and neither is
optional.

## What you get for giving that up

```ts
// Hono
const app = new Hono();
app.get("/users/:id", (c) => c.json({ id: c.req.param("id") }));
```

```ts
// AponiaJS
@Controller("users")
class UserController {
  constructor(private readonly users: UserService) {}

  @Get(":id")
  find(@Param("id") id: string) {
    return this.users.find(id);
  }
}
```

For one route, Hono is obviously better. The AponiaJS version starts paying off
when there are forty routes, a dozen services, and more than one team touching
them — [modules](/docs/essentials/modules) declare boundaries,
[providers](/docs/essentials/providers) are constructed once at startup, and
the graph is validated before the server listens.

Hono can be organised well; `app.route()` and per-file routers get you a long
way. It just does not have an opinion about how, and it has no container.

## Typed clients, two routes to the same place

Neither framework generates code. Hono RPC infers a client from the app type;
[Eden Treaty](/docs/elysia/eden-treaty) infers one from the composed Elysia
routes. The AponiaJS caveat is worth knowing before you plan around it:
decorator-wide Eden inference is not implemented, so full client types come
from statically composed native routes. It is in
[current limitations](/docs/project/current-limitations).

## Which one to pick

<ChoiceCards>
<Choice title="Choose Hono when">

- you deploy to the edge, or to more than one runtime;
- you want the smallest, fastest-to-start framework available;
- middleware composition is enough structure for your application;
- you are shipping to production now.

</Choice>
<Choice title="Choose AponiaJS when" tone="aponia">

- Bun is the only deployment target and that will not change;
- you want modules, controllers, and constructor injection rather than
  assembling a convention;
- Elysia is already the server;
- alpha software is acceptable for this codebase.

</Choice>
</ChoiceCards>
